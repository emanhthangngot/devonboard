# DevOnboard Q&A: System and Architecture (Technical)

This document prepares you for technical questions regarding DevOnboard's architecture, data models, and codebase retrieval pipelines.

---

### Q1: What is the core technology stack of DevOnboard?
*   **The Tech Stack**:
    *   **Backend**: Python 3.11+ using the **FastAPI** web framework. Dependencies are managed via the **`uv`** package manager.
    *   **Frontend**: **Next.js** (React, TypeScript) using vanilla CSS for UI styling.
    *   **Storage**: A local **JSON file** (`devonboard/knowledge-graph.json`) as the primary graph store.
    *   **AI/LLM**: **Gemini API** for rationale claim extraction, query routing, and grounded answer synthesis.
    *   **Vector Search (Optional)**: **Qdrant** for semantic retrieval over commit and claim texts.

---

### Q2: Why did you choose a JSON file for the Knowledge Graph instead of a graph database like Neo4j?
*   **The Architecture Choice**:
    *   **Portability & Simplicity**: A single JSON file is easy to inspect, debug, commit to Git, and ship. It requires zero database setup for developers during onboarding.
    *   **Fast In-Memory Traversal**: For single repositories, the graph is small enough to load into server memory (a few megabytes). In-memory Graph BFS/DFS traversal is extremely fast (under 1ms), avoiding network latency of external graph databases.
    *   **Optional Index Upgrades**: The backend is designed such that SQLite (for relational indexing) or Qdrant (for vector indexing) can be rebuilt as derived indexes from the authoritative JSON graph.

---

### Q3: How does the system extract "claims" and design decisions? Does it send everything to Gemini?
*   **The Ingestion Flow**:
    *   No, we do not send the entire codebase. We only send metadata from development activity (Git commit bodies, PR descriptions, and review comments) to Gemini.
    *   We use a conservative, structured extraction prompt that instructs Gemini to return a JSON schema containing only explicit design rationale, tradeoffs, and risks.
    *   If no explicit decisions are found in the commit text, the system skips claim creation. In the codebase, we also have a regex-based fallback parser (`rationale_extractor.py`) that searches for explicit keywords like "because", "so that", "tradeoff", and "risk".

---

### Q4: How does the query router decide between "structural", "historical", and "hybrid" modes?
*   **The Routing Logic**:
    *   **Structural**: Deals with how components call each other and code layout (e.g., *"Which modules call ProviderAdapter?"*).
    *   **Historical**: Deals with who, when, and why decisions were made (e.g., *"Why was memory progressive loading chosen?"*).
    *   **Hybrid**: Deals with refactoring risks and PR reviews (e.g., *"Is it safe to refactor ProviderAdapter?"*).
    *   The router parses the query keywords: terms like 'refactor', 'safe', 'risk' trigger `hybrid` routing; terms like 'why', 'rationale', 'decision' trigger `historical`; others default to `structural`. In the LLM-enabled pipeline, we prompt Gemini to classify the query route and identify starting search hints.

---

### Q5: How do you prevent duplicate nodes or edges when scanning a codebase or history multiple times?
*   **The Idempotency Rules**:
    *   Every node has a **deterministic identifier** generated by its properties. For example, a file node ID is always `file:{relative_file_path}`. A function node ID is `function:{filePath}:{functionName}`. A commit node is `source:commit:{commit_hash}`.
    *   During scanning or ingestion, the [graph_store.py](file:///home/pearspringmind/Hackathon/devonboard/backend/app/graph/graph_store.py) upsert function checks if the node ID exists. If it does, it merges incoming details (e.g., unioning tags, taking the latest summary, merging metadata) rather than adding a duplicate node, keeping the graph clean and idempotent.

---

### Q6: What role does Qdrant play in DevOnboard? Is it required to run the application?
*   **The Database Role**:
    *   **No, Qdrant is optional**. The application's core structural, historical, and hybrid retrieval runs entirely via graph traversal on the JSON Knowledge Graph.
    *   When Qdrant is enabled, it acts as a **semantic search accelerator**. It indexes the text of commit `source` nodes and design `claim` nodes. If a query cannot be matched via exact name strings, Qdrant helps find semantically similar nodes, which are then used as starting points for graph traversal.
